# Further standardization roadmap

The minimum implementation intentionally stops before organization-specific policy. These are the strongest next opportunities, in priority order.

1. **Organization preset and distribution.** Wrap the public initializer with organization defaults for ownership, data classification, approved stacks, internal registries, and support contacts. A team should ideally supply only a repository URL; do not add those organization-specific fields to the universal template.
2. **Policy-as-code controller.** Provision and continuously audit GitHub rulesets, security settings, environments, and allowed Actions from a reviewed organization repository. Keep project templates declarative and privileged mutation centralized.
3. **Control/evidence bill.** Make manifest control IDs first-class, map them to NIST SSDF outcomes, and export evidence through a recognized interchange such as OSCAL rather than inventing an ambiguous “bill of process” format. NIST frames SSDF as outcome-based and risk-adjusted: [NIST SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final); [NIST OSCAL](https://pages.nist.gov/OSCAL/) provides machine-readable control and assessment models.
4. **Reusable organization workflows.** Move common CI and release implementation into centrally maintained, SHA-pinned reusable workflows while leaving the repository manifest and required job names stable.
5. **Additional toolchains and stacks.** Add pnpm/Yarn/Bun and Poetry/PDM only as complete vertical slices: locked install, cache, BOM parsing, generated scripts, and regression renders. Add containers, infrastructure-as-code, data/ML, and mobile as separate profiles instead of weakening the base.
6. **Artifact provenance maturity.** Isolate release builds and verify attestations at consumption/deployment, aligning with [SLSA v1.2](https://slsa.dev/spec/v1.2/).
7. **Security posture evidence.** Add OpenSSF Scorecard and an organization dashboard for control drift. [OpenSSF Scorecard](https://openssf.org/scorecard/) should inform risk decisions rather than become a score target.
8. **Agent threat model profile.** For repositories that build agents or expose tools/MCP, add authorization, tool allowlists, data-flow classification, memory isolation, approval boundaries, and adversarial evals mapped to the [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/).
9. **Ownership and service catalog integration.** Generate CODEOWNERS, service metadata, on-call/runbook links, data classification, and lifecycle state from one organization catalog instead of asking each repository independently.
10. **Exception lifecycle and skill evals.** Centralize waivers with owner, expiry, compensating control, approval, reminders, and metrics. Maintain representative agent tasks to measure workflow success, unnecessary context, safety-boundary adherence, and regression rate before shared skill changes.

These patterns mirror the useful parts of WIPFU (progressive-disclosure task routing), Tincturo (canonical root guidance plus nested ownership/freshness metadata), and Receipt Engine (a machine-readable agent manifest and deterministic validators) without copying project-specific conventions into the universal baseline.
